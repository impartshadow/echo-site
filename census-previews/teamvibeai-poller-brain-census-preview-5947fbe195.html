Failure census preview — teamvibeai/poller-brain

Generated 2026-10-21 from 6 public issues. This is page one of a failure census: the dominant agent-failure classes in this project's own tracker, each with the deterministic check that would catch it.

The census splits into two tiers: structural code defects (unsafe regex scanning, incomplete checkpoint coverage, sentinel leakage) that produce wrong or lost data deterministically, and agentic-trust failures (false success signals, cross-boundary permission overreach) where the system reports a safe state that isn't true. Across all clusters the common thread is a mismatch between an internal 'success/safe' signal and externally observable ground truth, caught only by defensive re-verification rather than by the system itself.

unverified-push

Operations (sends, pushes, commits) report success without actual verification, so silently failed actions get trusted and the failure is only caught by a defensive re-check.

Evidence: “send_message reported success (or the session's own memory log claimed a message was sent) at least 3 separate times, but the message never actually appeared” — #499 #460 #462

The deterministic check: After any send/commit/push call, require an independent read-back (re-fetch thread/log/git status) that confirms the artifact exists before marking the step complete; block completion if read-back doesn't match claimed state.

capability-overreach

An agent claims or exercises access/permissions it shouldn't have across isolation boundaries (cross-brain repo writes), ignoring explicit anti-pattern guidance.

Evidence: “claims to have write access to a DIFFERENT channel's brain repo (erik-brain) than its own” — #528

The deterministic check: Add a pre-action gate that checks the target repo/channel against the acting brain's own channel ID; block any gh api/push/clone call where target != self, regardless of org membership claims.

unsafe-pattern-matching

Code uses an overly broad regex/scan assumption (full-document key scan) that breaks when the 'safe' assumption (no prose drift) turns out to be false, producing wildly wrong computed values.

Evidence: “pipe-table rows have no prose-drift risk — full `MEM-(\d+)` scan is safe and is defense-in-depth” — #486

The deterministic check: Restrict REGISTRY_KEY_PATTERN scanning to the actual key column (e.g. first pipe-table cell per row) via a column-anchored regex or structured table parse, and add a test with a MEM-<digits> token embedded in a Description cell asserting it is ignored.

edit-loop

Recurring, multi-cycle failures in the same skill/process (crash-safety checkpoints) keep recurring despite prior partial fixes, because each patch addresses only part of the failure window rather than the whole process.

Evidence: “This is the 5th consecutive consolidation lost mid-run on this brain” — #462 #460

The deterministic check: Require a commit/checkpoint after every discrete step group (not just some), verified by a post-run assertion that step count == commit count; block closing the issue until the checkpoint covers 100% of the step range, not just the previously patched subset.

sentinel-leak

An internal control-flow sentinel value meant to be silently intercepted is instead emitted as a real, user-visible message because the model wraps it in extra reasoning/tool calls instead of emitting it bare.

Evidence: “the NO_FURTHER_RESPONSE_NEEDED suppression sentinel repeatedly leaks as a real, visible Slack message instead of being silently dropped” — #451

The deterministic check: Add an output-gate contract that scans any outbound send_message payload for the sentinel literal and hard-blocks the call (not just exact-match on bare final text), regardless of surrounding reasoning tokens or tool-call wrapping.
