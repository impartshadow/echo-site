## Root-cause chain

1. Responses contained definitive availability, state, activity, verification, and completion claims unsupported by current evidence.
2. The agent treated memory, user framing, internal aliases, and git history as interchangeable with live ground truth.
3. Confidence language such as 'verified,' 'validated,' and completion phrasing masked the evidence mismatch.
4. Prompt-level instructions to read and verify did not reliably bind each claim to a same-turn artifact from the correct source class.
5. The harness has several narrow lexical and tool-presence gates, but lacks a unified claim-to-source suitability check before assertions leave the system.

## The contract that would have caught it

**`claim-source-suitability-gate`**

- **Trigger:** Any definitive claim about current vendor availability, repository completion, live process activity, quota state, or measured operational statistics.
- **Precondition:** Require same-turn provenance from an evidence source authorized for that claim class: vendor/public fetch for launch status, clean git status plus commit/push receipt for completion, process/session/quota inspection for live activity, and an identified tool output or artifact for statistics.
- **Why it catches this:** It would reject not only absent reads but also category errors: internal route probes used as vendor-launch evidence, git history used as runtime evidence, dirty worktrees paired with completion claims, and uncited figures or verification verbs lacking traceable artifacts.

## Why this matters

Prompt-only guardrails did not stop the model from sounding certain when its evidence was stale, absent, or from the wrong source class. Deterministic contracts blocked unsupported language and successfully stripped every repeated scaffold leak; extending that enforcement to claim-to-source suitability would close the central gap exposed by this trace.
