Failure census preview — NousResearch/hermes-agent

Generated 2026-08-16 from 6 public issues. This is page one of a failure census: the dominant agent-failure classes in this project's own tracker, each with the deterministic check that would catch it.

Across these six open issues, the recurring theme is a mismatch between what Hermes reports and what actually happened: components claim success (install pin, cron scheduling) or apply a static classification (reasoning-effort ladder, SSRF/private-IP check, modifier-key allowlist) without verifying it against the live, model- or environment-specific ground truth. A secondary pattern is missing user-facing signal during degraded states — long silent hangs with no interim feedback and no breaker escalation. Four of six issues are guard/mapping logic that trusts a fixed table or exit code instead of confirming the real-world outcome.

unverified-success-report

Tools and scripts report success to the user or the model without checking that the underlying action actually took effect — a commit pin that silently failed, and a cron job that can never fire because no gateway is running.

Evidence: “the installer still prints success and exits 0” — #87268 #87033

The deterministic check: Before returning success, the tool must assert the side effect actually landed (git HEAD == requested SHA; cron job has a live gateway/scheduler process to register with) and propagate any existing CLI-level warning (e.g. hermes_cli/cron.py's gateway check) into the tool result surfaced to the model — not just the human-facing CLI.

overzealous-guard-false-positive

Safety/input guards use brittle heuristics that misclassify legitimate cases as dangerous — an SSRF guard blocks real public sites because a VPN's DNS answers land in a reserved range, and a new input-safety gate swallows nearly all OS modifier-key chords instead of only the ones it's meant to catch.

Evidence: “classifies it as private/internal and blocks it” — #87106 #87140

The deterministic check: Guards must be tested against a fixed table of known-legitimate cases that must NOT be blocked (e.g. 198.18.0.0/15 resolving public hostnames, standard OS chords like Cmd+N/Cmd+T/Cmd+,) as a regression suite, and default to allow-with-log rather than hard-block when classification confidence is low or the allowlist is incomplete.

silent-hang-no-feedback

When a backend/provider wedges or a request stalls, the UI gives the user zero indication anything is wrong for very long periods, and the internal failure-detection ceiling never shortens or trips a breaker across repeated identical failures.

Evidence: “15 minutes of silence per attempt” — #87167

The deterministic check: Emit a UI-visible wait/heartbeat indicator once a request exceeds a fixed short threshold (e.g. 30s) independent of the final stale-stream kill ceiling, and assert the circuit breaker's failure counter increments and eventually opens after N consecutive same-endpoint timeouts rather than resetting on each new user-triggered retry.

wire-protocol-mapping-bug

Internal ladder names get remapped to the wrong wire-level value for a given backend model, sending a lower-capability parameter than the model actually supports even though a correct passthrough path already exists for a similar value.

Evidence: “xAI rejects `max`/`ultra` with `400 Invalid reasoning effort`” — #87279

The deterministic check: Unit test asserting `max`/`ultra` reasoning-effort aliases resolve per-model to that model's actual ceiling (e.g. grok-4.6 -> `xhigh`) via a maintained per-model ceiling table, not a single hardcoded fallback value shared across all models in the family.
