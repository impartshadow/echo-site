Failure census preview — reticlehq/reticle

Generated 2026-08-20 from 9 public issues. This is page one of a failure census: the dominant agent-failure classes in this project's own tracker, each with the deterministic check that would catch it.

Across these nine issues, reticle's tooling consistently reports success by checking the wrong layer — the DOM instead of app state, the repo instead of the deployed site, static config instead of a live round-trip, or a process-local flag instead of durable state. A second, smaller pattern is optimizations and safeguards that work in isolation but break their own contract at the boundary: a token-saving snapshot mode that strips the refs needed to act, and a benchmark harness with no timeout that can lose an entire run to one hung dependency.

false-green-action-dispatch

Reticle's write actions (check, drag) report success and dispatch DOM events, but never verify the application's actual state changed — so the tool lies about outcomes it never confirmed.

Evidence: “The DOM and the application disagree, and every read-only tool reports the DOM.” — #370 #250

The deterministic check: After any state-mutating action, assert the framework-level state (e.g. React controlled prop/store value, onDragEnd result) changed, not just the DOM property/attribute — fail the action if only the DOM moved.

false-green-install-verification

init, status, and doctor all report successful setup by checking local files and config shape, while the actual runtime path (ESM/CJS loadability, CSP-blocked websocket, deployed docs page, agent-to-app connection) is silently broken.

Evidence: “a setup step that exits 0 while leaving the user broken” — #379 #368 #269 #352

The deterministic check: Gate 'success' on an end-to-end round-trip: dev server actually boots and serves the page, the bridge websocket actually opens from the browser, and the deployed docs URL returns 200 — not just that the repo/config files are internally consistent.

stale-in-memory-state-reporting

The daemon tracks whether it has ever seen a session with a per-process in-memory flag, so any restart makes it falsely claim 'never seen one' even seconds after serving that exact session.

Evidence: “starts life believing nothing has ever connected to it” — #377

The deterministic check: Persist session-ever-connected state to disk (not a process-local boolean) so a restart can distinguish 'never wired' from 'restarted and lost state', and assert the two produce different messages.

unbounded-benchmark-hang

A stuck cell inside a third-party MCP dependency can hang the entire benchmark run forever with no timeout, silently destroying the whole pass instead of producing a partial or failed result.

Evidence: “A hung cell blocks the whole pass indefinitely” — #290

The deterministic check: Wrap each benchmark scenario in a hard per-scenario timeout; on expiry, kill the cell's subprocess and write a NOT MEASURED row instead of losing the entire run's analysis.json.

unusable-optimized-output

The delta-snapshot feature saves real tokens but strips ref markers via a shared normalization helper, so the cheaper response can never be acted on and the savings are illusory.

Evidence: “the delta output cannot be acted on” — #258

The deterministic check: Add a contract test asserting every snapshot mode combination (including diff:true) returns at least one actionable ref when the underlying elements have refs — fail the build if a cheaper mode strips required identifiers.
