Failure census preview — EliteaAI/elitea_issues

Generated 2026-08-25 from 6 public issues. This is page one of a failure census: the dominant agent-failure classes in this project's own tracker, each with the deterministic check that would catch it.

The dominant pattern across these issues is loss of ground truth: either observability data silently fails to reach Analytics/execution-history despite correct billing, or execution state (tool_call_id, error status, run status) silently diverges from what actually happened, letting failures pass through as apparent success. A smaller subset concerns runs lacking hard lifecycle bounds (heartbeat, cancel, timeout) to recover from crashes.

silent-observability-gap

LLM calls and agent runs happen and get billed correctly, but the audit trail feeding Analytics/execution history silently drops rows for certain trigger paths, leaving no way to diagnose failures or verify spend.

Evidence: “does not show up anywhere in Elitea's Analytics” — #6309 #6364 #6363

The deterministic check: assert that every LLM call event recorded in the LiteLLM/usage ledger has a corresponding row in the analytics ingestion table, keyed by request_id, before the billing period closes

unnormalized-resume-state

Chat interface resume paths reconstruct AIMessage objects from checkpoint data without applying the same tool_call_id normalization used elsewhere, so a None tool_call_id survives into tool execution and fails validation.

Evidence: “reconstructs `AIMessage` objects from checkpoint data” — #6353

The deterministic check: assert tool_call_id is not None on every ToolMessage constructed in resume paths (MCP auth, parallel sub-agent, HITL) before invoking tool execution

silent-failure-passthrough

Provider and MCP tool failures are detected and logged but execution continues as if nothing went wrong, so agents and pipelines see successful output where an actual error occurred.

Evidence: “the agent or pipeline sees an error where it previously saw successful output” — #6401

The deterministic check: assert that any tool/provider response classified as status Error/Failed or isError=true raises ToolException before the middleware returns control to the calling agent

unbounded-run-lifecycle

Evaluation runs previously had no durability guarantees against worker crashes, no cancellation support, and no time budget, so a stuck or crashed run could stay 'running' forever.

Evidence: “a stuck or crashed run could stay "running" forever with no way to recover or stop it” — #6398

The deterministic check: assert every run row has a heartbeat updated within a bounded interval or is auto-transitioned to a terminal status by the reaper, and every run has time_budget_seconds enforced server-side
